# 1. アーキテクチャ概要

## 1.1 レイヤ構造

```
[必須] 静的PWA        GitHub Pages等。全グループ共用の1デプロイ
[必須] ストレージ      グループごとに選択(S3互換/Drive/Dropbox/WebDAV)。データの正本
[必須] inbox          ストレージネイティブの上り経路(presigned PUT等)
[任意] サーバーレス関数 Web Push配送のみ。GAS / Cloudflare Workers の2実装
[保険] メール(mailto)  外部API依存ゼロの手動一括送信
[併設] 公開サイト      紹介ページ・プライバシーポリシー・導入手順書(同一静的ホスト)
```

- データの正本は常にストレージ。関数・ローカルDBはいつでも再構築できる
- 認証・アクセス制御はサーバーではなく暗号(E2EE+鍵所持)で実現する

## 1.2 依存性ポリシー

| 層 | 実装 | 障害・撤退時 |
|---|---|---|
| 静的ホスト | GitHub Pages(第一) | 任意の静的ホストへ移設 |
| ストレージ | S3互換(リファレンス) / Drive / Dropbox / WebDAV | プロバイダ抽象で差替 |
| 関数 | GAS / Workers(同一HTTP契約) | 差替またはメールへ縮退 |
| メール | mailto:(基本) / GAS MailApp(格上げ) | mailtoが最終フォールバック |
| フォント | Zen Maru Gothic / Noto Sans JP を woff2 で同梱 | 外部CDNへは接続しない |

# 2. テナントモデル(マルチグループ)

## 2.1 グループ

グループ=ストレージルート1つ+鍵体系1つ。グループ間で共有される状態は存在しない。

- 同一人物が複数グループの管理者/メンバーになれる。グループごとに独立した鍵ペア・キーストアを持つ
- ストレージはグループごとに自由(同一Driveの複数フォルダ、グループごとに別プロバイダ、いずれも可)
- IndexedDBはグループIDで名前空間を分離する

## 2.2 接続コード

端末がグループに接続するための位置情報。秘密情報ではない。

```json
{
  "v": 1,
  "group_id": "...",
  "provider": "s3 | gdrive | dropbox | webdav | http",
  "root": "バケットURL/フォルダID等",
  "pepper": "KDF用ペッパー",
  "adminPublicKey": "管理者のECDSA公開鍵 (base64, raw)"
}
```

`adminPublicKey` が**信頼の根**である。名簿ファイル自身が名乗る公開鍵は信用せず、必ずこのコードの鍵と一致することを確認してから署名検証する。これにより、ストレージを完全に掌握した攻撃者でも偽の名簿を通せない(紙の配布物を差し替えない限り)。`pepper` と併せて、接続コードは「秘密ではないが、無いと安全に参加できない」位置づけになる。

base64エンコードした文字列およびQRコードとして紙の入会案内に記載する。読取はカメラ(`BarcodeDetector`、非対応時は WASM デコーダへフォールバック)または文字列貼り付け。
入会案内3点セット: **接続コード + ログインID + 初期パスワード**。

## 2.3 グループ切替UI

- ワークスペース型スイッチャーで複数グループを行き来する(design 11)
- 複数グループ管理者向け横断ダッシュボード: 各グループの未処理inbox件数・未送信通知・メール未登録者数を一覧表示

# 3. スコープ(配信範囲)設計

## 3.1 スコープの種類

| スコープID | 内容 | メンバー |
|---|---|---|
| `all` | グループ全体 | 全メンバー |
| `staff` | 担当者のみ | 管理者 + 担当者 |
| `sg_{id}` | サブグループ | 所属メンバー |

## 3.2 サブグループ階層

サブグループは親子関係を持つ木構造とする。深さの上限は設けない(UIは2階層までを想定)。

```
all
├ staff
└ sg_a (Aチーム)
  ├ sg_a_pickup (送迎係)
  └ sg_a_event  (イベント準備)
```

**階層は「所属の伝播」と「UI表示」にのみ効き、鍵の派生関係は持たない。**

- 名簿生成時、子サブグループの所属者には親サブグループの所属も自動付与する(`sg_a_pickup` の所属者は `sg_a` と `all` にも所属する)
- 各スコープは独立したAES鍵を持つ。親の鍵から子の鍵を導出しない
- 結果として「親宛の配信は子のメンバーにも届く」「子宛の配信は子の中だけ」が自然に成立する(design 08 の「この中だけ」)

この設計により、階層が深くなっても復号ロジックは「自分が持つ鍵で開けるか」だけで済み、鍵の派生ミスによる越境閲覧が構造的に起こらない。

## 3.3 複数スコープ配信

1つのメッセージを複数スコープへ同時配信する(design 06 の「届ける相手: Aチーム + 送迎係」)。
オブジェクトは単一の鍵で暗号化せず、**コンテンツ鍵(CEK)を毎回ランダム生成し、宛先スコープ数だけラップする**(§4.4)。

# 4. 暗号設計

## 4.1 プリミティブ

| 用途 | アルゴリズム | 実装 |
|---|---|---|
| コンテンツ暗号化 | AES-256-GCM | Web Crypto |
| 鍵交換・ラップ | ECDH P-256 + HKDF-SHA256 + AES-GCM | Web Crypto |
| 署名 | ECDSA P-256 | Web Crypto |
| パスワードKDF | Argon2id(WASM: hash-wasm) | ライブラリ |
| 乱数・ID | crypto.getRandomValues | Web Crypto |

## 4.2 鍵階層

```
管理者ルート鍵 (ECDSA署名鍵。信頼の根)
    │ 署名
    ▼
名簿 roster.sig.json (全メンバーの公開鍵 + サブグループ木を含む)
    │ 各メンバー公開鍵で ECIES ラップ
    ▼
スコープ鍵 (AES-256。all / staff / sg_*。世代管理あり)
    │ CEK をラップ
    ▼
コンテンツ鍵 CEK (AES-256。オブジェクトごとにランダム)
    │ 暗号化
    ▼
コンテンツ (メッセージ・添付・イベント・設定)
```

- 各オブジェクトのヘッダに宛先の `key_id`(`scope:vN`)を平文で列挙し、ローテーション後も旧データを復号可能にする
- **staff スコープ鍵**: 参加者の連絡先(メールアドレス)等、担当者・管理者のみ復号可能な領域に使用
- 名簿は公開部(表示名・公開鍵・所属スコープ・サブグループ木)と、staffスコープで暗号化された連絡先部の2部構成

## 4.3 キーストア(パスワードログイン)

```
ログイン: 接続コード + ID + パスワード
  ① filename = SHA-256(group_id + login_id) でキーストアを特定
  ② users/{filename}.enc を公開読みで取得
  ③ KEK = Argon2id(パスワード, salt, pepper)
  ④ KEKでキーストア復号 → 個人秘密鍵(ECDH/ECDSA)を取得
  ⑤ keyring/ から自分宛ラップ分を復号 → 所属スコープの鍵を取得
```

- サーバー不在のため認証=復号成功。任意端末からログイン可、端末に鍵を縛らない
- **オフライン総当たり対策**(公開ストレージのため必須):
  1. Argon2idをメモリハード設定で使用
  2. 初期パスワードはランダム生成(単語4つ方式等)。ユーザー変更時は強度チェック必須
  3. ペッパー(グループ共通のランダム秘密値)を接続コードにのみ載せ、ストレージには置かない
- キーストアのファイル名をハッシュにするのは在籍者列挙の防止のため
- ログイン失敗時のメッセージは「アカウント不存在」と「パスワード誤り」で同一にする

## 4.4 エンベロープ形式(マルチレシピエント)

すべての暗号化オブジェクトは以下の自己記述バイナリで包む。

```
offset 0        : magic "MFN1"                       (4 bytes)
offset 4        : version = 2                        (1 byte)
offset 5        : recipient count R (1..255)         (1 byte)
per recipient   : keyId 長 (1) + keyId (UTF-8)
                + wrapped 長 (1) + wrapped
                  wrapped = IV(12) || AES-GCM(scopeKey, CEK 32B)  = 60 bytes
then            : body IV (12 bytes)
then            : ciphertext = AES-GCM(CEK, plaintext), AAD = 先頭からbody IVまでの全ヘッダ
```

- `keyId` を平文で置くのは、鍵を持たない段階で「自分に開けるか」を判別するため
- ヘッダ全体を AAD に含めるため、宛先リストの改竄・差し替えは復号失敗として検出される
- 単一スコープのオブジェクト(キーストア・設定・名簿の staff 部)は R=1 の特殊ケースとして同じ形式を使う
- 復号は「自分が持つ鍵と一致する最初の `keyId` を選び、CEK を unwrap して本体を開く」

## 4.5 重複排除

重複排除は**平文のSHA-256を暗号化メタデータの内側**に持ち、同一スコープ内でのみ判定する(平文ハッシュを外に出すと内容確認攻撃を許すため)。

## 4.6 フォーム回答・不在連絡の暗号化

- 回答はエフェメラルECDH+AES-GCMで**フォーム作成者の公開鍵**に対して暗号化する(受信者=個人なのでスコープ鍵は使わない)
- 転記経路(管理者PWA・関数・ストレージ)は中身を復号できない
- 運用選択で管理者リカバリ鍵にも併せてラップ可能(作成者の端末・パスワード喪失対策。リカバリ鍵は普段オフライン保管)
- 不在連絡の宛先は `staff` スコープ

## 4.7 ローテーション・失効

- 退会時: **退会者が所属していた全スコープ**の鍵を新世代に更新し、残メンバーへ再ラップ。以後の新規コンテンツは旧メンバーには復号不能
- サブグループの鍵ローテーションは親・子へ波及しない(§3.2 のとおり派生関係がないため)
- 過去データの再暗号化はオプション(添付の量に応じて判断)
- 所属変更(サブグループ間の移動)は、抜けたスコープの鍵ローテーション+名簿の所属変更として処理
- メンバー一括入替(年度更新相当)は、名簿の一括書き換え+影響スコープの一括ローテーションを1トランザクションとして実行する

## 4.8 管理者ルート鍵の保全

- 開設ウィザードの最終ステップで紙のリカバリキット(バックアップコード印刷)を必須手順とする
- ルート鍵は管理者のキーストア内に保存。リカバリキットからの復元手順を提供

# 5. 認証・メンバー管理フロー

## 5.1 入会

```
管理者: メンバー登録(氏名・所属サブグループ) → 初期パスワード生成 → 紙の3点セット印刷
参加者: 接続コード読取(QR/文字列) → ID+初期パスワードでログイン       (design 01)
      → 初回ウィザードでメールアドレス入力(必須。未登録中は閲覧ロック)  (design 02)
      → テスト通知の受領を本人が確認 → 入力内容はinbox経由で管理者へ
管理者: 名簿に反映 → 入会成立
```

- 管理者によるメンバー登録時に個人鍵ペアを事前生成しキーストアに格納する方式(初期パスワードで封緘)とし、初回ログイン時に本人がパスワード変更する

## 5.2 パスワード管理

- 変更: 本人がアプリ内で実施。キーストアを新KEKで再暗号化しinbox経由で更新(個人秘密鍵は不変のため再ラップ不要)
- 忘れ: 管理者が再発行(新鍵ペア+新初期パスワード、スコープ鍵再ラップ)。データはストレージから再同期されるため損失なし

## 5.3 退会

名簿から削除 → 所属していた全スコープの鍵ローテーション → push購読レジストリから削除。

## 5.4 端末の登録解除

design 12 の「この端末の登録を解除」は以下を行う。鍵はサーバー側に無いため、他端末のログインには影響しない。

- 当該グループの IndexedDB(復号済みキャッシュ・添付blob・送信待ちキュー)を削除
- push購読を解除し、inbox経由で購読レジストリからの削除を依頼
- 既知グループレジストリから当該グループを除去

送信待ちキューが残っている場合は警告し、同期後に実行させる。

# 6. 同期・イベント設計

## 6.1 イベントソーシング

- すべての変更を events/ への追記イベントとして表現する。イベントファイルは1変更1ファイル(追記専用のため書き込み競合が発生しない)
- ファイル名 `{timestamp}-{random}` は時系列ソート可能。クライアントは sync_state のカーソル(最終処理イベント)以降のみを範囲取得する
- イベントの本文(author, target, 参照先)は暗号化し、外に出るメタデータを最小化する

## 6.2 可変ファイルの扱い

- 可変ファイルは manifest.json / roster.sig.json / keyring / キーストア / settings に限定し、更新者を管理者(+本人のキーストア)に絞ることでlast-writer-wins競合を実務上排除する
- それ以外の状態変化はすべてイベントに寄せる

## 6.3 オフライン

- 投稿・回答: ローカルDBに保留キューとして保存し、オンライン復帰時に送信
- 閲覧: IndexedDBから表示
- 同期状態(最終同期時刻・保留件数)を表示し、手動同期を提供する(design 12)

## 6.4 未読管理

未読は各端末のローカル計算のみで行う(要件書§4.10)。

- `sync_state.lastReadAt` と各メッセージの作成時刻を突き合わせて未読を判定する
- 既読情報の上り送信は行わない。したがって担当者側に「誰が未読か」を出す画面は作らない
- 複数端末間で未読状態は共有されない(受容済み制約)

## 6.5 IndexedDB(Dexie.js)

```
mofune_{group_id}
├ messages      # 復号済みキャッシュ
├ files         # blob キャッシュ(容量上限つきLRU)
├ events        # 処理済みイベント
├ roster        # 名簿 + サブグループ木
├ outbox        # 送信待ちキュー
└ sync_state    # カーソル・鍵世代・lastReadAt
```

# 7. ストレージ設計

## 7.1 StorageProvider抽象

```typescript
interface StorageProvider {
  get(path: string): Promise<Uint8Array>
  put(path: string, data: Uint8Array): Promise<void>      // 要書き込み権限(担当者)
  list(prefix: string, after?: string): Promise<Entry[]>  // カーソル付き範囲取得
  delete(path: string): Promise<void>
  capabilities: {
    inbox: boolean          // 匿名アップロード経路の有無
    publicRead: boolean
  }
}
```

## 7.2 プロバイダ能力マトリクス

| プロバイダ | 公開読み | inbox | inbox方式 |
|---|---|---|---|
| S3互換(R2/B2/MinIO) | ○ | ○ | presigned PUT |
| WebDAV / NAS | ○ | ○ | ユーザー別Basic認証 |
| Google Drive | ○ | × | -(上り機能を使う場合は非推奨) |
| Dropbox | ○ | × | 同上 |

開設ウィザード(design 10)はこの表をそのまま選択肢として提示し、inbox 非対応を選んだ場合は「不在連絡・フォーム回答が使えない」ことを選択前に明示する。

## 7.3 ストレージレイアウト

```
/{group_id}/
├ manifest.json          # 平文: フォーマット版数・鍵世代・関数URL・通知チャネル設定
├ roster.sig.json        # 名簿。公開部+staff部、管理者ルート鍵で署名
├ keyring/
│   └ v{NNN}.json        # 各スコープ鍵をメンバー公開鍵でラップ。世代管理
├ users/
│   └ {hash}.enc         # キーストア。hash = SHA-256(group_id + login_id)
├ events/
│   └ {ts}-{rand}.enc    # イベントログ(追記専用)。ファイル名は時系列ソート可能
├ messages/  *.enc
├ files/     *.enc
├ forms/     *.enc       # フォーム定義(メッセージから参照)
├ settings/
│   └ templates.enc      # メールテンプレート・定型理由等。管理者編集
├ inbox/
│   └ {user_id}/         # 上り投函先
└ invites/               # 招待の一時データ
```

平文で露出するのはオブジェクトのサイズ・更新時刻・パス構造・宛先 key_id のみ(許容メタデータ、要件書§5.3)。

# 8. inbox設計

- 参加者の上り(不在連絡・フォーム回答・メアド登録・キーストア更新・push購読)はすべてinbox経由に一本化
- S3互換: 管理者PWAが開いた時に各ユーザーのアップロード用presigned PUT URLを発行(有効期限付き、キーはランダム化)し、各人の鍵で暗号化して配布。参加者PWAはPUTするだけ
- WebDAV: ユーザー別Basic認証
- 投函物は宛先(staffスコープまたはフォーム作成者)の鍵で暗号化済み。inboxの傍受・改竄では内容が漏れない
- 管理者PWAが開いた時にinboxを回収し、正規領域(events等)へ転記。閲覧側は「events+自分宛inbox直読み」で転記遅延の影響を受けない

# 9. 通知設計

## 9.1 チャネル抽象と受信者解決

```typescript
interface NotificationChannel {
  publish(notice: Notice): Promise<void>   // 投稿者のブラウザから実行
}
// 実装: WebPushChannel(関数経由) / MailtoChannel
```

投稿完了時、投稿者のPWAが受信者ごとに解決する:

```
サブグループの通知が停止中 → 対象外
push購読あり かつ 関数healthy(GET /health, 短タイムアウト) → Web Push
上記で届かない受信者 → メール対象リストへ → mailtoバッチUI表示
最終保証 → アプリ起動時同期
```

通知はすべて無内容(「Mofuneに新着があります」+リンク)。

## 9.2 通知設定の粒度

| 設定 | 主体 | 保存先 | 画面 |
|---|---|---|---|
| サブグループ単位の通知停止 | 管理者 | manifest.json | design 08 |
| チャネル既定(push/メール) | 管理者 | manifest.json | design 08 |
| 個人のpush購読 | 本人 | 購読レジストリ(関数) | design 12 |
| 個人のメール受信可否 | 本人 | 名簿 staff 部 | design 12 |

配信対象は「スコープのメンバー ∩ サブグループ通知が有効 ∩ 個人設定が有効」で決まる。

## 9.3 Web Push(関数層経由)

- 無内容push(ペイロード空)でService Workerを起こすのみ。RFC 8291のペイロード暗号化実装を不要化
- SWはpushイベントで汎用通知を表示する
- iOSはホーム画面追加が前提。オンボーディングに導線を組み込む
- 購読フロー: 参加者PWAで購読 → PushSubscriptionをinboxへ投函 → 管理者PWAが回収し関数へレジストリ更新

## 9.4 メール(mailto)

- 宛先は**BCC**に自動設定(参加者間のアドレス秘匿)。TOはグループの共用アドレス
- 件名・本文は settings/templates.enc から復号して生成。プレースホルダは `{{グループ名}} {{リンク}} {{種別}}` 程度に限定し、メッセージ本文は埋め込まない(平文経路のため)
- **バッチ分割**: URL長上限を超える場合は自動分割し、「メールを開く (1/3)…」のリンク列+送信済みチェックUIを表示。1バッチ件数は設定値(実機検証で既定値決定、§15)
- 送信元はグループの共用メールアカウントをメーラーに設定する運用を手順書に記載
- 送信状況(未送信バッチ・メール未登録者数)は管理者ダッシュボードに表示(design 08/11)
- 関数層(GAS)導入グループはMailAppによる自動送信へ格上げ。mailtoは常に残る最終手段

# 10. 関数層(任意)

## 10.1 HTTP契約

```
POST /notify         { group_id, scope_id, auth }    # 無内容pushを該当購読者へ送信
POST /subscriptions  { group_id, registry, auth }    # 管理者PWAが購読名簿を差替
GET  /health
```

- 1デプロイで複数グループを担当(registry・authトークンはgroup_id単位)
- 保持する状態は購読レジストリとVAPID秘密鍵のみ。すべて管理者PWAから再投入可能な「再構築可能キャッシュ」であり、関数はいつでも別実装へ差替可能
- 漏洩時の被害範囲は無内容pushのスパム送信のみ(コンテンツ鍵に触れない)
- cron(時間トリガー)導入時は締切リマインド等の時限通知も担当可能

## 10.2 実装

| | GAS | Cloudflare Workers |
|---|---|---|
| 対象 | Googleアカウントのみのグループ(非エンジニア本命) | 技術者のいるグループ / Google回避 |
| VAPID署名 | jsrsasign等を同梱(ES256) | Web Crypto |
| 購読保存 | PropertiesService / Drive | Workers KV |
| メール格上げ | MailApp | -(mailtoのまま) |
| 展開 | テンプレコピー→承認(未確認アプリ警告を手順書で突破)→デプロイ | ダッシュボード手動作成手順 |

- Firebase Functionsはデプロイに従量課金プラン(カード登録)が必要なため優先度低(採用時要確認)
- 関数URLはmanifest.jsonに記載。再デプロイ・移行はmanifest書き換えのみ

# 14. セキュリティ考察(脅威モデル要約)

| 脅威 | 対策 |
|---|---|
| ストレージURL流出・第三者の覗き見 | E2EE。鍵なしでは全データ復号不能 |
| キーストアのオフライン総当たり | Argon2id+生成パスワード+ペッパー(§4.3) |
| 名簿改竄・偽メンバー混入 | 管理者ルート鍵による名簿署名 |
| 宛先スコープの差し替え | エンベロープヘッダ全体をAADに含める(§4.4) |
| 参加者間の連絡先漏洩 | staffスコープ鍵+BCC送信 |
| フォーム回答の覗き見(管理者含む) | 作成者公開鍵への暗号化 |
| 子サブグループ宛の内容が親に漏れる | スコープ鍵は独立生成。派生関係を持たない(§3.2) |
| 関数の侵害 | 無内容通知のためスパム送信以外の被害なし |
| 退会者のアクセス継続 | 所属全スコープの鍵ローテーション(既取得データは回収不能=受容済み) |
| 閲覧行動のプロファイリング | 既読情報を一切送出しない(§6.4) |
| inboxへのスパム投函 | presigned URLの期限・ランダムキー。E2EEにより改竄・盗聴は無効 |
