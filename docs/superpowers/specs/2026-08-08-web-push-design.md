# Web Push (関数層) 設計 (2026-08-08)

設計書 §9.1 / §9.3 / §10 を実装に落とす。ブラウザからは Web Push を送れない
(送信には VAPID 秘密鍵と push サービスへの直接 POST が要る) ので、任意の関数層を
1つ置く。**置かなくても全機能が動く**という前提は変えない。

## 何を作るか

1. **Cloudflare Workers の関数** (`functions/workers/`)
   - `GET /health` — 生きているか。投稿側は短いタイムアウトで叩き、駄目ならメールへ落とす
   - `POST /subscriptions` — 管理者の端末が購読名簿を丸ごと差し替える
   - `POST /notify` — 該当スコープの購読者へ**無内容**の push を送る
2. **アプリ側**
   - 参加者: 設定画面で購読を作り、inbox へ投函する (原稿 12)
   - 管理者: 受信箱から購読を回収し、関数へ名簿を差し替える
   - 投稿後: 関数が healthy なら `/notify`、駄目ならこれまで通り mailto バッチ
   - Service Worker: `push` で汎用通知を出し、`notificationclick` でアプリを開く

## 決めたこと

- **push の中身は空**。RFC 8291 のペイロード暗号化を実装しないで済む。本文は
  端末が鍵を持って取りに行く。通知に出るのは「Mofune に新しい連絡があります」だけ
- **関数が持つ状態は購読名簿と VAPID 秘密鍵のみ**。どちらも管理者の端末から
  入れ直せる。漏れても被害は無内容 push のスパムに限られ、本文の鍵には触れない
- **認証はグループごとの共有トークン**。`Authorization: Bearer <token>` を
  定数時間で比較する。トークンは `settings/notifications.enc` (staff スコープ) に置く
- **購読は inbox 経由**。参加者は関数の URL もトークンも持たない。関数を
  差し替えても参加者の端末は何も知らないままでよい
- **購読名簿はスコープごとの束**。`/notify` は `scope_id` で引くだけにして、
  関数側に名簿や所属の知識を持たせない
- **関数の URL は manifest.json** (平文)。再デプロイは manifest の書き換えだけ

## やらないこと

- cron による締切リマインド — 関数に時間を持たせると「再構築可能キャッシュ」から
  はみ出る。作成者がアプリを開いたときに送る方式は現状のままにする
- ペイロード付き push — 通知に本文を載せない方針そのもの

## GAS 版 (2026-08-08 に追加)

Google アカウントだけのグループ向けに、同じ契約の Apps Script 版を置いた
(`functions/gas/`)。判断は `logic.js` の1枚に閉じ込め、Workers 版と同じ
振る舞いを vitest で縛っている。Google の API に触るのは `Code.gs` だけ。

Apps Script には3つの制約があり、クライアント側で呼び分ける:

| | Workers | Apps Script |
|---|---|---|
| 行き先 | `…/notify` | `…/exec?path=/notify` (パスを持てない) |
| 合言葉 | `Authorization` ヘッダ | 本文の `token` (独自ヘッダは preflight を呼び、答えられない) |
| 失敗の伝えかた | 401 / 400 | 200 + `{"error":…}` (状態コードを選べない) |

ES256 の署名だけは自前で持てないので jsrsasign を同じプロジェクトへ貼る。
秘密鍵は PEM で渡す (PKCS#8 の base64url ではない)。


## 通知の届き先の決めかた (設計書 §9.1)

投稿した端末が受信者ごとに解決する。

```
サブグループの通知が止まっている → 対象外
購読があり、関数が healthy      → Web Push
それ以外                        → メール対象 → mailto バッチ (実装済み)
最終保証                        → 起動時同期 (実装済み)
```

## 実装して分かったこと (2026-08-08)

- **署名する相手は購読ごとの URL ではなく push サービスのオリジン**。endpoint を
  そのまま `aud` にすると、どのサービスも 401 を返す
- **`navigator.serviceWorker.ready` は登録が無いと永久に解決しない**。実機で
  「登録しています…」のまま固まった。`getRegistration()` で先に有無を確かめる
- **許可のプロンプトは応答が返らないことがある**。上限を置いて、返らなければ
  「端末の設定から許可してください」と伝える
- **受け皿 (SW) の確認を許可より先に**行う。渡す先が無いのに許可だけ求めても、
  答えを活かせない
- 関数は**どの人へ送れたかを返す** (`notified`)。返さないと、投稿側は push が
  届いた人にもメールを出すことになる。関数が知るのは不透明な userId だけ
- ローカル検証は `functions/workers/src/handler.ts` を esbuild で束ね、素の
  node で 8788 番に立てた。ブラウザからの preflight を含む CORS もこれで確かめた

## 置き場の判定 (2026-08-08 に整理)

置き場に必要なのは2つだけ。**パスから URL を組み立てられること**と、
**参加者が資格情報なしに1つ置けること** (presigned か、関数層の引換券)。

| 置き場 | 判定 |
|---|---|
| S3 互換 (R2 / B2 / Wasabi / MinIO / Storj / Supabase / GCS 互換API) | いまの `S3StorageProvider` がそのまま使える見込み。要確認は公開読み・CORS・presigned の3点 |
| WebDAV (Nextcloud / NAS) | 実装済み。**公開共有の起点にパスを継ぎ足せる**のが決め手。presigned が無いので上りは関数層の引換券 (関数に NAS の資格情報を持たせる。任意) |
| Google Drive | 実装済み。Apps Script が**所有者権限で動く**ため OAuth が誰にも要らない |
| Box / OneDrive / SharePoint / Dropbox | 見送り。共有リンクがファイルごとの不透明な URL で、パスから組み立てられない。書きは OAuth 専用で、関数に預けるとしても Drive のような「OAuth ゼロ」にならない |
| iCloud Drive | 不可。公開 API が無い |
| GitHub / GitLab のリポジトリ | 技術的には可・運用で不可。履歴が永久に残り添付を消せない |

WebDAV で実装のうえ気をつけた点:

- **親フォルダが無いと PUT は 409**。S3 のようにキーを置くだけでは済まないので、
  断られたら上から順に掘って置き直す (掘った階層は覚えて二度掘らない)
- 一覧は `PROPFIND` の `Depth: 1`。答えには**フォルダ自身が必ず入る**ので外す
- `DOMParser` は実行環境に無いことがあるため、名前空間の接頭辞に寛容な取り出しを自作した
- `capabilities.inbox` は false。参加者が自分で置く道が無いことを型で示す

## 差分同期の最適化 (2026-08-08)

2つ直した。

1. **カーソル以降だけを頼む**。一覧できる置き場では `list(prefix, after)` に
   カーソルをパスへ直して渡す (S3 の start-after、関数の `/list` の `after`)。
   索引しか読めない参加者の経路は丸ごと読むしかないので、そこは手元で絞る
2. **本文はまとめて取り、並びどおりに適用する**。1件ずつ待つと往復の回数だけ
   待たされる (初回の同期がとくに遅い)。同時に走らせるのは4本まで。
   **適用は必ず順番どおり**で、取れなかったものが出たらそこでカーソルを止める
   (次の同期で拾い直す)

取得を並行にすると、失敗したときの扱いを間違えやすい。カーソルを「最後に
**適用できた**もの」で進めるようにして、欠けたものを飛び越さないようにした。
