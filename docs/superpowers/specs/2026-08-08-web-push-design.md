# Web Push (関数層) 設計 (2026-08-08)

設計書 §9.1 / §9.3 / §10 を実装に落とす。ブラウザからは Web Push を送れない
(送信には VAPID 秘密鍵と push サービスへの直接 POST が要る) ので、任意の関数層を
1つ置く。**置かなくても全機能が動く**という前提は変えない。

## 何を作るか

1. **Cloudflare Workers の関数** (`functions/workers/`)
   - `GET /health` — 生きているか。投稿側は短いタイムアウトで叩き、駄目ならメールへ落とす
   - `POST /subscriptions` — 管理者の端末が購読名簿を丸ごと差し替える
   - `POST /notify` — 該当スコープの購読者へ**無内容**の push を送る
2. **アプリ側**
   - 参加者: 設定画面で購読を作り、inbox へ投函する (原稿 12)
   - 管理者: 受信箱から購読を回収し、関数へ名簿を差し替える
   - 投稿後: 関数が healthy なら `/notify`、駄目ならこれまで通り mailto バッチ
   - Service Worker: `push` で汎用通知を出し、`notificationclick` でアプリを開く

## 決めたこと

- **push の中身は空**。RFC 8291 のペイロード暗号化を実装しないで済む。本文は
  端末が鍵を持って取りに行く。通知に出るのは「Mofune に新しい連絡があります」だけ
- **関数が持つ状態は購読名簿と VAPID 秘密鍵のみ**。どちらも管理者の端末から
  入れ直せる。漏れても被害は無内容 push のスパムに限られ、本文の鍵には触れない
- **認証はグループごとの共有トークン**。`Authorization: Bearer <token>` を
  定数時間で比較する。トークンは `settings/notifications.enc` (staff スコープ) に置く
- **購読は inbox 経由**。参加者は関数の URL もトークンも持たない。関数を
  差し替えても参加者の端末は何も知らないままでよい
- **購読名簿はスコープごとの束**。`/notify` は `scope_id` で引くだけにして、
  関数側に名簿や所属の知識を持たせない
- **関数の URL は manifest.json** (平文)。再デプロイは manifest の書き換えだけ

## やらないこと

- GAS 実装 — Workers と同じ HTTP 契約なので後から足せる。まず1つ通す
- cron による締切リマインド — 関数に時間を持たせると「再構築可能キャッシュ」から
  はみ出る。作成者がアプリを開いたときに送る方式は現状のままにする
- ペイロード付き push — 通知に本文を載せない方針そのもの

## 通知の届き先の決めかた (設計書 §9.1)

投稿した端末が受信者ごとに解決する。

```
サブグループの通知が止まっている → 対象外
購読があり、関数が healthy      → Web Push
それ以外                        → メール対象 → mailto バッチ (実装済み)
最終保証                        → 起動時同期 (実装済み)
```
