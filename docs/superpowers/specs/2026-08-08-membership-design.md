# メンバーの追加とパスワード再発行 設計

**日付:** 2026-08-08
**対象:** デザイン 09 のうち、鍵の入れ替えを伴わない範囲
**状態:** 承認済み

## 解く問題

いまグループに入れるのは**開設時に登録した人だけ**。あとから人を入れる手立てが無く、
実運用に出せない。

## 決めたこと

- **初期パスワードは管理者が決めて紙で渡す。** 開設時と同じやり方に揃える。管理者が
  一時的に初期パスワードを知ることは受け入れる(本人が後で変更する経路は別途)
- **今回は追加・一覧・パスワード再発行まで。** 削除と年度更新はスコープ鍵の
  ローテーションが要るので別の設計にする

## 追加の流れ

管理者だけが行える。名簿の再署名に必要な ECDSA 秘密鍵を持つのが管理者だけのため。

```
1. 新メンバーの ECDH / ECDSA 鍵ペアと userId を作る
2. キーストアを初期パスワードで封緘して users/ へ置く
3. いまの keyring に、新メンバー宛のラップを足す
4. 名簿に1人足し、連絡先を staff 部へ入れ、世代を上げて再署名する
5. 参加者なら投函枠を配る
```

**keyring の世代は上げない。** 世代は鍵そのものが変わったときのためにある。追加は
既存の鍵を新しい相手にも配るだけなので、同じ世代の `wrapped` に足すのが正しい。
世代を上げると manifest も更新することになり、全端末が読み直す羽目になる。

**追加した人は過去のお知らせも読める。** スコープ鍵が同じだから当然そうなる。
これは仕様であり、隠したいなら鍵のローテーション(=削除と同じ仕組み)が要る。
画面にその旨を出す。

## パスワード再発行の流れ

**鍵ペアごと作り直す。** 管理者は本人の秘密鍵を取り出せない(本人のパスワードで
包まれている)ので、「同じ鍵のままパスワードだけ変える」ことは原理的にできない。

```
1. 新しい鍵ペアを作り、新しいパスワードでキーストアを封緘して置き換える
2. keyring の各エントリで、その人の古いラップを新しい公開鍵のものに差し替える
3. 名簿のその人の公開鍵を差し替え、世代を上げて再署名する
4. 参加者なら投函枠を配り直す (古い枠は新しい鍵で開けない)
```

**副作用がある。** 古い端末に残っている未送信の投函は開けなくなる。再発行は
「パスワードを忘れた」ときの操作であり、頻繁に押すものではないことを画面に書く。

## 画面

`/g/:groupId/members`(管理者のみ)。ルータの meta に `adminOnly` を足す。

- 名簿の一覧(表示名・役割・所属)
- 追加フォーム(表示名・ログインID・役割・初期パスワード・メール)
- 各行に「パスワードを再発行」

## やらないこと

- 削除・年度更新(鍵のローテーション)
- サブグループ間の移動(サブグループ管理と一緒にやる)
- 一括操作・検索(人数が増えてから)
