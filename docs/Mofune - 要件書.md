# グループ連絡PWAアプリ Mofune 要件書

改訂: 2026-08-07 (rev.2 — デザイン確定を受けた汎用グループ化)
本書は仕様検討の議論を経て確定した要件を定義する。実現方式は設計書に記す。

---

# 1. 目的・背景

グループ内の連絡(お知らせ・写真・不在連絡・フォーム)を行うPWAアプリを提供する。
対象は幼稚園・保育園に限らず、名簿を持ち定期的に一斉連絡を行うあらゆる小規模グループ(園、学童、マンション管理組合、サークル、地域団体、部活動など)とする。

- 運営者(開発者)は中央サーバー・データベースを一切保有しない
- 各グループが自分のアカウントで持つ外部ストレージをデータ基盤とする
- 利用グループ数・ユーザー数が増えても運営者側のコスト・運用負荷が増えない
- 恒久的な無料枠のみで運用可能であること

---

# 2. 用語

| 用語 | 定義 |
|---|---|
| グループ | 運用単位のテナント。データ・鍵・名簿が完全に独立する |
| サブグループ | グループ内の配信単位(例: Aチーム、送迎係)。入れ子にできる |
| 管理者 (admin) | グループの開設者・運営責任者。鍵管理・メンバー管理を担う |
| 担当者 (staff) | 投稿権限を持つメンバー |
| 参加者 (member) | 閲覧と上り送信(不在連絡・フォーム回答)を行うメンバー |
| スコープ | 配信範囲=鍵の単位。`全体` / `担当者のみ` / 各サブグループ |
| 接続コード | ストレージ種別とルート位置を示すコード(QR/文字列)。秘密情報ではない |
| キーストア | ユーザーの秘密鍵一式をパスワード由来鍵で暗号化したファイル |
| inbox | 参加者からの上りデータの投函先。ユーザーごとに分離 |
| 無内容通知 | 本文を含まず「新着がある」事実のみ伝える通知 |

UIの表示名は汎用語(グループ/サブグループ/管理者/担当者/参加者)で固定する。用途別の言い換え(園/クラス/園長/先生/保護者など)は行わない。

---

# 3. ロールと権限

| 操作 | 管理者 | 担当者 | 参加者 |
|---|---|---|---|
| 閲覧 | ○ | ○ | ○(所属スコープのみ) |
| 投稿・添付・フォーム作成 | ○ | ○ | × |
| 不在連絡・フォーム回答 | ○ | ○ | ○ |
| 通知送信 | ○ | ○(投稿時) | × |
| メンバー管理・サブグループ管理・鍵管理 | ○ | × | × |
| グループ設定(テンプレート等) | ○ | × | × |

サブグループの作成・改称は管理者のみ。メンバーの所属変更は管理者が行う。

# 4. 機能要件

## 4.1 メッセージ・ファイル共有

- 担当者はメッセージを作成し、グループ全体または任意のサブグループへ配信できる
- **1つのメッセージを複数のスコープへ同時に配信できる**(例: Aチーム + 送迎係)
- メッセージには写真・PDF等のファイルを添付できる。添付は複数可
- 参加者(該当スコープのメンバー)以外は、ストレージのURLを知っていてもファイル・メッセージの内容を閲覧できないこと

## 4.2 サブグループ

- グループの下にサブグループを作成できる。サブグループはさらに入れ子にできる
- 1人が複数のサブグループに所属できる
- 子サブグループのメンバーは親サブグループのメンバーでもある(所属は上位へ自動的に含まれる)
- 親サブグループ宛の配信は子のメンバーにも届く。子サブグループ宛の配信は**その子の中だけ**に届く
- サブグループ単位で通知の停止・再開ができる

## 4.3 埋め込みフォーム

- 担当者はメッセージにフォーム(選択式・記述式等)を埋め込める
- 参加者はアプリ内でフォームに回答できる
- 回答は**フォーム作成者(送信者)のみ**が閲覧・集計できる。経路上の第三者(管理者含む)は内容を読めないこと
- 回答の締切を設定でき、未回答者に催促を送れる
- 集計結果をCSV等で書き出せる
- 端末紛失時の回答復旧のため、管理者が保持するリカバリ鍵を併用可能とする(運用選択)

## 4.4 不在連絡

- 参加者は不在連絡を送信できる
- 種別は「欠席 / 遅れます / 早く帰ります」から選択し、対象日を指定する
- よく使う理由を定型選択肢から選べる。定型選択肢はグループ設定として管理者が編集できる
- 内容は宛先(担当者・管理者)のみ閲覧可能

## 4.5 通知

- 投稿時に対象メンバーへ通知する。アプリを閉じていても気づけること
- 通知チャネルは多段構成とし、上位が使えない場合は自動的に下位へフォールバックする
  1. Web Push(関数層を導入したグループのみ・自動)
  2. メール(手動一括送信。mailto:リンクで担当者のメーラーを開き、宛先をBCCに自動設定)
  3. アプリ起動時同期(最終保証)
- 通知はすべて無内容通知とする。本文・個人情報を通知経路に載せない
- メール宛先が多くURL長制限を超える場合は自動でバッチ分割し、送信済み管理UIを提供する
- メール文面はテンプレート化し、グループ設定として暗号化保存・管理者編集可能とする
- 通知のオン/オフはサブグループ単位(管理者)と個人単位(本人)の両方で設定できる

## 4.6 メンバー管理

- 入会: 紙(またはQR)で「接続コード+ログインID+初期パスワード」を配布する
- **メールアドレス登録を入会の必須条件とする**。未登録の間は主要機能をロックする
- メールアドレスの到達確認(テスト通知→アプリ内で受領確認)を行う
- 参加者間で互いのメールアドレス・連絡先は閲覧不可とする
- メンバーの検索・複数選択・サブグループへの一括移動ができる
- 退会処理後、退会者は以後の新規コンテンツを閲覧できないこと
- メンバーの一括入替(進級・卒業・年度替わりに相当する処理)に対応する

## 4.7 認証

- ログインID+パスワードのみでログインできる。参加者はGoogle等のアカウント・ストレージのアカウントを一切必要としない
- 接続コードはQRコード読取(カメラ)または文字列入力で受け付ける
- 任意の端末からログイン可能(端末に鍵を縛らない)。機種変更・複数端末利用に対応
- パスワード変更は本人が実施可能。パスワード忘れは管理者による再発行で回復
- 端末のローカルデータを消去する「この端末の登録を解除」を提供する

## 4.8 複数グループ

- 1人が複数グループの管理者・メンバーになれる
- グループごとにストレージを自由に選択できる。同一アカウント内の複数フォルダ運用も可
- アプリはグループ切替UIを持つ。複数グループ管理者向けの横断ダッシュボードを提供する
- 関数層は1デプロイで複数グループを担当できる

## 4.9 オフライン

- 閲覧はオフラインで可能(ローカルDBから表示)
- 投稿・回答はオフライン時にローカル保存し、オンライン復帰後に同期する
- 同期状態(最終同期時刻・保留件数)を画面上で確認でき、手動同期を実行できる

## 4.10 未読管理

- 未読件数・未読バッジは**各端末のローカル計算のみ**で行う
- 誰が読んだか・誰が未読かを他メンバーへ共有する機能は提供しない。上りの既読通信を一切行わない

## 4.11 公開サイト

アプリ本体とは別に、静的ホスティング上へ以下の公開ページを用意する。

- 紹介トップページ(できること・安心のしくみ・はじめかた・FAQ・仕組みの説明)
- プライバシーポリシー
- 導入手順書(管理者向けセットアップ手順。スクリーンショット付き)

公開ページの記述は、実装済みの機能と検証済みの事実のみを述べること。無料・費用に関する記述は「Mofuneの利用料が無料である」ことに限定し、グループが用意するストレージ側の料金・登録条件と混同させない。

# 5. 非機能要件

## 5.1 インフラ・コスト

- アプリは静的ホスティング(GitHub Pages等)のみで配信する
- 中央サーバー・常駐プロセス・常時稼働端末を必要としない
- 必須構成は恒久無料で運用できること
- サーバーレス関数は「あると体験が良くなる層」であり、無くても全機能が動作すること(通知の自動化のみ低下)

## 5.2 依存性(ベンダーロックイン回避)

各層で特定サービスへの依存を持たない。

| 層 | 要件 |
|---|---|
| 静的ホスト | 任意の静的ホストで動作 |
| ストレージ | プロバイダ抽象化。S3互換・Google Drive・Dropbox・WebDAV等を差し替え可能 |
| inbox | ストレージネイティブ機構のみで実現(関数に依存しない) |
| 関数 | 共通HTTP契約に対し複数実装(GAS / Cloudflare Workers)。差し替え・撤去可能 |
| メール | mailto:による手動送信を基本とし外部API依存ゼロ。関数導入時は自動送信に格上げ可 |
| フォント・アセット | すべて自ホストに同梱する。実行時に外部CDNへ接続しない |

## 5.3 セキュリティ・プライバシー

- 全コンテンツをE2E暗号化する。ストレージは公開(リンク到達で読める)前提でも安全であること
- ストレージ事業者・関数のいずれもコンテンツを復号できないこと
- 通知経路(push/メール)に個人情報・本文を載せない
- フォーム回答は送信者のみ復号可能
- 参加者の連絡先は担当者・管理者のみ復号可能
- 公開ストレージ前提のオフライン総当たり攻撃に対抗する(強KDF・生成パスワード・ペッパー併用)
- 閲覧行動(誰がいつ読んだか)はサーバー・他メンバーのいずれにも送出しない
- メタデータ(オブジェクトサイズ・更新時刻・アクセスパターン・通知発生時刻)の漏洩は許容し、プライバシーポリシーに明記する

## 5.4 UI・アクセシビリティ

- デザインシステム(キャラクター「モフネ」・配色・タイポグラフィ・モーション)を全画面で統一する
- 配色のコントラストは WCAG 2.1 AA を満たす
- `prefers-reduced-motion` が有効な端末ではキャラクターのアニメーションを停止する
- 表示言語は日本語。文言は幼稚園に限定しない汎用語を用いる

## 5.5 スケーラビリティ

- グループ単位で完全独立(水平分割)。グループ数に上限なし
- 1グループあたり数百名規模を想定

## 5.6 運用性

- 非エンジニアの管理者が、スクリーンショット付き手順書に従ってグループを開設できること(ストレージ準備・関数展開含む)
- 開設ウィザードはストレージの接続確認(読み書きテスト・inbox作成)を含む
- 管理者ルート鍵の紙のリカバリキット作成を開設手順に含める

# 6. 受容済みの制約(トレードオフ)

以下は設計判断として受け入れた制約であり、グループへの説明資料・プライバシーポリシーに明記する。

1. Web Push自動通知は関数層を導入したグループのみ。iOSはPWAのホーム画面追加が必須
2. mailto:によるメール送信は担当者の手動操作であり、送信完了の機械的検証はできない(自己申告チェック+管理者画面での送信状況可視化で運用カバー)
3. 退会者が在籍中に取得済みのデータは回収できない
4. 時限通知(締切リマインド等)は誰かがアプリを開いた時に起動する(関数層導入時はcronで自動化)
5. パスワード忘れの自動リセットはない(管理者再発行)
6. Google Drive・Dropboxはinbox(上り)非対応のため、上り機能を使うグループはS3互換ストレージまたはWebDAVを選択する
7. 未読・既読の共有を行わないため、担当者は「誰が読んでいないか」を把握できない。到達確認はフォーム回答で代替する
8. 通知送信状況の集計は端末ローカルの送信記録に基づき、受信側の実受信を保証しない

# 7. 対象外

- ネイティブアプリ(ストア配布)
- リアルタイムチャット(双方向即時メッセージング)
- 課金・決済
- 運営者による集中監視・サポート基盤
- 既読の共有・閲覧履歴の可視化
- ntfy等の公共Push中継の利用(rev.1で検討したが、iOSでの信頼性・自PWAでの受信不可・説明負債のため不採用)
